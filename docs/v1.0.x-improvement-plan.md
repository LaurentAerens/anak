## 🔍 Detailed Analysis & Root Causes of Rejected Candidates

### 1. Step 1.1: Incremental `PawnKey` in `Board` (-2.7 Elo)
- **Hypothesis:** Eliminating `ComputePawnKey` loops in `CorrectionHistory` by maintaining `ulong PawnKey` incrementally in `Board` would accelerate leaf evaluation.
- **Root Cause of Regression:** `MakeMove` and `UnmakeMove` execute millions of times per node across the entire search tree. In contrast, `CorrectionHistory` is only probed at leaf evaluation or quiet move cutoffs. Copying and maintaining extra `PawnKey` fields on every move imposed a per-node tax that outweighed the small savings of lazily bit-scanning 8–12 pawns on demand.

### 2. Step 1.3: SIMD Fused Accumulator (0 NPS gain)
- **Hypothesis:** Combining copy, add, and sub into a single pass would save memory bandwidth.
- **Root Cause:** In modern CPUs (L1 cache = 32-48 KB), a 512-short (1 KB) accumulator fits entirely in L1 cache. The memory bus was never bottlenecked; compiler loop unrolling and register utilization in separate loops was already optimal.

### 3. Step 1.5: 4-Row Register Blocking in `ComputeHiddenLayer` (-39% NPS)
- **Hypothesis:** Computing 4 output hidden layer neurons concurrently would reuse activation vectors in registers.
- **Root Cause:** AVX2 only provides 16 YMM registers. Accumulating 4 output neurons simultaneously requires 4 accumulator registers, 4 weight vector registers, activation registers, plus widening scratch registers. RyuJIT ran out of registers and spilled vectors to stack memory on every loop iteration, causing a catastrophic 39% slowdown.

### 4. Step 1.7: Managed Array `ulong[]` Repetition Table (-9.9 Elo)
- **Hypothesis:** Replacing inline struct `RepetitionTable` with `ulong[]` would reduce `Board` struct size.
- **Root Cause:** In C#, `Board` is a struct copied by value (e.g. `Board searchBoard = _board;` in UCI and helper workers). Making `_history` a managed `ulong[]` caused both root and search boards to share the exact same underlying array reference. Search plies overwrote the real game history, causing false threefold repetition claims during winning games and missed repetitions when losing. Abandoned permanently.

### 5. Step 2.1: Eager Quiet Move Scoring in `MovePicker` (Timeouts)
- **Hypothesis:** Scoring all quiet moves upfront would optimize sort time.
- **Root Cause:** The vast majority of nodes produce a beta cutoff on the TT move, winning captures, or killer moves. Scoring all quiet moves upfront pays a heavy sorting tax on nodes where quiet moves are never even traversed.

## 🚀 Detailed Summary of Accepted Improvements

### 1. `v1.0.1` — 1D Flattened `ContinuationHistory` Table (+3.1 Elo, +5.8% NPS)
- **Files Modified:** `src/Anak.Search/Minimax/History/ContinuationHistory.cs`
- **Mechanism:** Replaced 4D managed arrays `int[13, 64, 13, 64]` with flat 1D array `int[16 * 64 * 16 * 64]` using branchless bitwise index calculation: `((p1 << 16) | (to1 << 10) | (p2 << 6) | to2)`. Eliminates .NET multi-dimensional array lookup math and bounds checks while improving L1/L2 cache locality.

### 2. `v1.0.2` — Inline Fixed `Mailbox Piece[64]` in `Board` (+6.3 Elo, 97.9% LOS)
- **Files Modified:** `src/Anak.Core/Board/Board.cs`, `src/Anak.Core/Board/Fen.cs`
- **Mechanism:** Added an inline value buffer `[InlineArray(64)] public struct Mailbox` inside `Board`. Eliminates the 7-branch bitboard chain in `Board.GetPieceAt` (`Occupied`, `White`, `Pawns`, `Knights`, `Bishops`, `Rooks`, `Queens`, `Kings`), accelerating Static Exchange Evaluation (SEE), MovePicker move ordering, and tactical cutoffs.

### 3. `v1.0.3` — Bypass Micro-NNUE Accumulators in Search (+4.1 Elo, 90.7% LOS)
- **Files Modified:** `src/Anak.Data/Nnue/MultiTierNnueEvaluator.cs`, `docs/FUTURE_IDEAS.md`
- **Mechanism:** Removed `_stackMicroWhite` and `_stackMicroBlack` vector copying and `UpdateMove` calculations across every node in `AlphaBeta` and `QuiescenceSearch`. Micro-NNUE is only used at root for candidate move blunder checking and now evaluates on demand using a stackalloc 16-short buffer.

## 📋 Complete Active Work Queue for Tomorrow & Beyond (Targeting `v1.0.4+`)

Here are all the remaining active improvement candidates from the plan, organized in order of execution:

### 1. Step 2.2 — Capture History Malus on Failed Captures *(Bucket 2: Search Efficiency)*
- **Files:** `src/Anak.Search/Minimax/AlphaBetaEngine.cs`, `src/Anak.Search/Minimax/History/CaptureHistory.cs`
- **Concept:** In `AlphaBetaEngine.cs`, track searched captures. When a beta cutoff occurs, apply a negative score penalty (gravity-damped malus) to previously searched captures that failed to produce a cutoff (`_captureHistory.Update(piece, to, victim, -bonus)`). Pushes losing/refuted captures down the move ordering list in subsequent nodes.
- **SPSA Needed:** No.

### 2. Step 2.3 — Transposition Table Move Ordering in Quiescence Search *(Bucket 2: Search Efficiency)*
- **Files:** `src/Anak.Search/Minimax/QuiescenceSearch.cs`
- **Concept:** In `QuiescenceSearch.cs`, probe the TT for a valid hash move at shallow plies (or depth 0 / root of QSearch). If present and valid, give it highest move ordering priority (`int.MaxValue / 2`) so the hash move is searched first before generating other captures.
- **SPSA Needed:** No.

### 3. Step 1.9 — Dedicated Tactical Move Generator (`GenerateCapturesAndPromotions`) for QS *(Bucket 1: Speedup)*
- **Files:** `src/Anak.Core/MoveGen/MoveGenerator.cs`, `src/Anak.Search/Minimax/QuiescenceSearch.cs`
- **Concept:** When not in check (~90% of QSearch nodes), `QuiescenceSearch` currently generates all legal quiet moves only to filter them out (`if (!m.IsCapture && !m.IsPromotion) continue;`). Since QSearch represents 75–85% of all nodes, adding a dedicated `GenerateLegalTacticalMoves` (masks targets with `enemyPieces`, skips quiet pawn pushes and castling) eliminates generating dozens of discarded quiet moves per QSearch node.
- **SPSA Needed:** No.

### 4. Step 1.4 — Lazy NNUE Accumulator Evaluation on Stack *(Bucket 1: Speedup)*
- **Files:** `src/Anak.Data/Nnue/MultiTierNnueEvaluator.cs`
- **Concept:** Currently, `PushMove` eagerly updates the full NNUE accumulator on every move. If a node immediately produces a TT cutoff, 50-move draw, or is in check and never calls `Evaluate()`, that accumulator computation was wasted. Delaying computation until `Evaluate()` is actually invoked saves work on cut nodes.
- **SPSA Needed:** No.

### 5. Step 1.4b — Bulk Incremental Feature Updates in `NnueAccumulator` *(Bucket 1: Speedup)*
- **Files:** `src/Anak.Data/Nnue/NnueAccumulator.cs`
- **Concept:** Batch piece additions and removals into combined SIMD feature pointers, vectorizing weight additions and subtractions to minimize inner loop branching during incremental accumulator updates.
- **SPSA Needed:** No.

### 6. Step 2.4 — Correction History Bound Filtering, Depth Weighting & Scaling *(Bucket 2: Search Efficiency)*
- **Files:** `src/Anak.Search/Minimax/History/CorrectionHistory.cs`, `src/Anak.Search/Minimax/AlphaBetaEngine.cs`
- **Concept:** Only update `CorrectionHistory` when the TT bound justifies the direction (`Exact`, `LowerBound && score > staticEval`, or `UpperBound && score < staticEval`). Weight updates by depth using gravity damping and clamp applied adjustments to a tunable `CorrHistMaxCp` (default 128).
- **SPSA Needed:** Yes (tune `CorrHistMaxCp` and `CorrHistWeight`).

### 7. Step 2.5 — Singular Extensions: Multi-Cut Pruning & Negative Extensions *(Bucket 2: Search Efficiency)*
- **Files:** `src/Anak.Search/Minimax/AlphaBetaEngine.cs`
- **Concept:**
  - **Multi-Cut:** In singular verification search, if `sScore >= beta`, another move already beats beta at reduced depth — return `sScore` immediately without searching the remaining tree.
  - **Negative Extension:** If `sScore >= singularBeta` and `ttScore >= beta`, other moves are also strong, so `ttMove` is not singular — reduce depth (`singularExtension = -1`).
- **SPSA Needed:** Optional (tune `SingularMargin` if needed).

### 8. Step 2.6 — Reuse Cached Capture SEE in Main Search + Shallow SEE Pruning *(Bucket 2: Search Efficiency)*
- **Files:** `src/Anak.Search/Minimax/MovePicker.cs`, `src/Anak.Search/Minimax/AlphaBetaEngine.cs`
- **Concept:**
  - `MovePicker.ScoreCaptures()` already evaluates SEE for all captures and categorizes them into `MovePickerStage.BadCaptures`. `AlphaBetaEngine.cs` currently calls `StaticExchangeEvaluator.Evaluate` a second time! Reuse the existing stage flag.
  - Add shallow SEE pruning for quiet moves and bad captures at `depth <= 5` with tunable margins (`SeeQuietMargin`, `SeeCaptureMargin`).
- **SPSA Needed:** Yes (tune `SeeQuietMargin` and `SeeCaptureMargin`).

### 9. Step 2.7 — Comprehensive History-Biased LMR & Pruning SPSA Tuning *(Bucket 2: Search Efficiency)*
- **Files:** `src/Anak.Search/Minimax/AlphaBetaEngine.cs`, `tools/tuning/spsa.py`
- **Concept:** Recalibrate LMR reduction formulas, RFP/NMP pruning margins, and ContinuationHistory bonus/penalty scales across tournament games after all structural changes are in place.
