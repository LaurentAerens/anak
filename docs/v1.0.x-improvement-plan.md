## 🔍 Detailed Analysis & Root Causes of Rejected Candidates

### 1. Step 1.1: Incremental `PawnKey` in `Board` (-2.7 Elo)
- **Hypothesis:** Eliminating `ComputePawnKey` loops in `CorrectionHistory` by maintaining `ulong PawnKey` incrementally in `Board` would accelerate leaf evaluation.
- **Root Cause of Regression:** `MakeMove` and `UnmakeMove` execute millions of times per node across the entire search tree. In contrast, `CorrectionHistory` is only probed at leaf evaluation or quiet move cutoffs. Copying and maintaining extra `PawnKey` fields on every move imposed a per-node tax that outweighed the small savings of lazily bit-scanning 8–12 pawns on demand.

### 2. Step 1.3: SIMD Fused Accumulator (0 NPS gain)
- **Hypothesis:** Combining copy, add, and sub into a single pass would save memory bandwidth.
- **Root Cause:** In modern CPUs (L1 cache = 32-48 KB), a 512-short (1 KB) accumulator fits entirely in L1 cache. The memory bus was never bottlenecked; compiler loop unrolling and register utilization in separate loops was already optimal.

### 3. Step 1.5: 4-Row Register Blocking in `ComputeHiddenLayer` (-39% NPS)
- **Hypothesis:** Computing 4 output hidden layer neurons concurrently would reuse activation vectors in registers.
- **Root Cause:** AVX2 only provides 16 YMM registers. Accumulating 4 output neurons simultaneously requires 4 accumulator registers, 4 weight vector registers, activation registers, plus widening scratch registers. RyuJIT ran out of registers and spilled vectors to stack memory on every loop iteration, causing a catastrophic 39% slowdown.

### 4. Step 1.7: Managed Array `ulong[]` Repetition Table (-9.9 Elo)
- **Hypothesis:** Replacing inline struct `RepetitionTable` with `ulong[]` would reduce `Board` struct size.
- **Root Cause:** In C#, `Board` is a struct copied by value (e.g. `Board searchBoard = _board;` in UCI and helper workers). Making `_history` a managed `ulong[]` caused both root and search boards to share the exact same underlying array reference. Search plies overwrote the real game history, causing false threefold repetition claims during winning games and missed repetitions when losing. Abandoned permanently.

### 5. Step 2.1: Eager Quiet Move Scoring in `MovePicker` (Timeouts)
- **Hypothesis:** Scoring all quiet moves upfront would optimize sort time.
- **Root Cause:** The vast majority of nodes produce a beta cutoff on the TT move, winning captures, or killer moves. Scoring all quiet moves upfront pays a heavy sorting tax on nodes where quiet moves are never even traversed.

### 6. Step 1.9: Dedicated Tactical Move Generator for QS (-6.4 Elo)
- **Hypothesis:** Generating only captures and promotions when `!inCheck` in `QuiescenceSearch` would eliminate generating and filtering dozens of discarded quiet moves.
- **Root Cause:** While it achieved a +5.4% NPS speedup in isolated benchmarks, in fast tournament play against `v1.0.3` it altered subtle move-ordering tie breakers among equal-scoring captures in QSearch selection sort, yielding a net negative match record (505 / 1029, -6.4 &plusmn; 21.7 Elo). Repurposed and added to `docs/FUTURE_IDEAS.md` scoped exclusively to the root blunder checker.

### 7. Step 1.4: Lazy NNUE Accumulator Evaluation on Stack (-19.5 Elo)
- **Hypothesis:** Deferring accumulator vector copy and incremental update until `Evaluate()` is invoked would save work on cut nodes.
- **Root Cause:** In short time controls, checking dirty stack flags and looking up stack metadata inside the critical leaf evaluation path adds branching overhead. Additionally, falling back to full `ComputeFull` when non-evaluating evasion plies precede a leaf evaluation introduces latency spikes during sharp tactical exchanges, causing a net negative match result (236 / 500, -19.5 &plusmn; 31.1 Elo). Eager incremental updates remain superior.

### 8. Step 1.4b: Bulk Incremental Feature Updates in Accumulator (-8.4 Elo)
- **Hypothesis:** Fusing piece additions and subtractions into single-pass SIMD updates (`Update1Add1Sub` and `Update1Add2Sub`) would cut accumulator memory loads/stores by 50–67% and eliminate loop overhead.
- **Root Cause:** Loading and widening 2–3 feature weight vectors concurrently inside the inner SIMD loop doubles register pressure (requiring 8–11 SIMD registers). On modern x86 hardware with 32–48 KB L1 cache, sequential single-feature updates with 128-bit SIMD (`SubFeature` then `AddFeature`) run with minimal register pressure (only 4–5 registers) and execute cleanly out of L1 cache. The increased register contention and cache footprint in the fused loop resulted in lower overall search throughput (256k vs 300k NPS) and net negative match performance (243.0 / 498, -8.4 &plusmn; 22.8 Elo). Individual feature update loops remain superior.

### 9. Step 2.3: Transposition Table Move Ordering in Quiescence Search (-16.7 Elo)
- **Files Modified:** `src/Anak.Search/Minimax/QuiescenceSearch.cs`
- **Mechanism:** Probed TT in quiescence search leaf nodes and prioritized `entry.BestMove` over MVV-LVA captures.
- **Root Cause:** Although benchmark tree size dropped by -8.2% (719k to 660k nodes), 250-game sanity check against baseline `v1.0.4` yielded **-16.7 &plusmn; 34.1 Elo** (47.60%, 16.7% LOS). Prioritizing TT moves and bypassing delta/SEE pruning in QS caused tactical inaccuracies when TT entries were upper bounds or stale. Cleanly reverted.

### 10. Step 2.5: Singular Extensions Multi-Cut & Negative Extensions (-2.5 Elo)
- **Files Modified:** `src/Anak.Search/Minimax/AlphaBetaEngine.cs`
- **Hypothesis:** Multi-Cut prunes search when an alternative move beats beta at reduced depth; negative extension (`singularExtension = -1`) searches non-singular moves shallower.
- **Root Cause:** While fixed-depth bench nodes dropped by -28.5%, it was an illusion: searching non-singular moves 1 ply shallower caused tactical blind spots in complex positions. When the TT move failed low, the engine either played an inferior move or wasted time researching. Over 5,376 games vs `v1.0.5`, it yielded **-2.5 &plusmn; 7.9 Elo** (49.63%). Cleanly reverted.

### 11. Step 2.10: Fail-Soft Quiescence Search `bestScore` Tracking (-20.9 Elo)
- **Files Modified:** `src/Anak.Search/Minimax/QuiescenceSearch.cs`
- **Hypothesis:** Tracking `bestScore` in QS and returning fail-soft scores (and storing `bestScore` in TT) would improve score accuracy for `AlphaBeta` and `CorrectionHistory`.
- **Outcome:** 250-game sanity check against `v1.0.6` scored **117.5 / 250 (47.00%)**, yielding **-20.9 &plusmn; 38.0 Elo** (13.9% LOS).
- **Root Cause:** Quiescence search is an asymmetric cut-off heuristic: captures with `SEE < 0` and moves failing delta pruning are pruned entirely without search. Because unsearched captures are pruned, any score `< alpha` does NOT represent the true minimax value of the tactical position. Leaking incomplete, pruning-skewed floor values into parent PVS re-search windows and TT bounds causes search instability. Classical engines intentionally keep QS fail-hard on `alpha`. Cleanly reverted.

## 🚀 Detailed Summary of Accepted Improvements

### 1. `v1.0.1` — 1D Flattened `ContinuationHistory` Table (+3.1 Elo, +5.8% NPS)
- **Files Modified:** `src/Anak.Search/Minimax/History/ContinuationHistory.cs`
- **Mechanism:** Replaced 4D managed arrays `int[13, 64, 13, 64]` with flat 1D array `int[16 * 64 * 16 * 64]` using branchless bitwise index calculation: `((p1 << 16) | (to1 << 10) | (p2 << 6) | to2)`. Eliminates .NET multi-dimensional array lookup math and bounds checks while improving L1/L2 cache locality.

### 2. `v1.0.2` — Inline Fixed `Mailbox Piece[64]` in `Board` (+6.3 Elo, 97.9% LOS)
- **Files Modified:** `src/Anak.Core/Board/Board.cs`, `src/Anak.Core/Board/Fen.cs`
- **Mechanism:** Added an inline value buffer `[InlineArray(64)] public struct Mailbox` inside `Board`. Eliminates the 7-branch bitboard chain in `Board.GetPieceAt` (`Occupied`, `White`, `Pawns`, `Knights`, `Bishops`, `Rooks`, `Queens`, `Kings`), accelerating Static Exchange Evaluation (SEE), MovePicker move ordering, and tactical cutoffs.

### 3. `v1.0.3` — Bypass Micro-NNUE Accumulators in Search (+4.1 Elo, 90.7% LOS)
- **Files Modified:** `src/Anak.Data/Nnue/MultiTierNnueEvaluator.cs`, `docs/FUTURE_IDEAS.md`
- **Mechanism:** Removed `_stackMicroWhite` and `_stackMicroBlack` vector copying and `UpdateMove` calculations across every node in `AlphaBeta` and `QuiescenceSearch`. Micro-NNUE is only used at root for candidate move blunder checking and now evaluates on demand using a stackalloc 16-short buffer.

### 4. `v1.0.4` — Capture History Malus on Failed Captures (+8.2 Elo, 99.9% LOS)
- **Files Modified:** `src/Anak.Search/Minimax/AlphaBetaEngine.cs`, `src/Anak.Search/Minimax/MovePicker.cs`
- **Mechanism:** Track searched captures at each search node and apply a gravity-damped negative penalty (`-bonus`) to previously searched captures whenever a beta cutoff occurs. Scaled capture history in `MovePicker` (`/ 16`) and clamped good captures to `Math.Max(0, ...)` to refine capture move ordering without overriding MVV-LVA or erroneously demoting good captures to bad captures. Achieved **+8.2 &plusmn; 5.4 Elo** across a full 10,000-game match with **99.86% LOS**.

### 5. `v1.0.5` — Correction History Bound Filtering, Depth Weighting & Scaling (+204.5 Elo, 100% LOS)
- **Files Modified:** `src/Anak.Search/Minimax/History/CorrectionHistory.cs`, `src/Anak.Search/Minimax/AlphaBetaEngine.cs`
- **Mechanism:** Fixed critical algorithmic bugs in pawn correction history: enforced strict bound filtering (LowerBound only updates when `score > staticEval`; UpperBound only when `bestScore < staticEval`; mate scores excluded), introduced depth-weighted exponential moving average (EMA) convergence, and clamped applied adjustments to a safe `[-128, +128]` cp window. Slashed benchmark tree size by **-45.9%** (from 719k to 389k nodes) and achieved **+204.5 &plusmn; 7.1 Elo** across a full 10,000-game match (**76.44% score**, 6,969 W / 1,680 L / 1,351 D) with **100% LOS**. Estimated Anak Elo increased to **2487 &plusmn; 7**.

### 6. `v1.0.6` — Cached Capture SEE in MovePicker & Shallow SEE Pruning (+16.3 Elo, 100% LOS)
- **Files Modified:** `src/Anak.Search/Minimax/MovePicker.cs`, `src/Anak.Search/Minimax/AlphaBetaEngine.cs`
- **Mechanism:** 
  1. Cached the Static Exchange Evaluation in `MovePicker._seeScores` and exposed `CurrentSee` property, eliminating duplicate `StaticExchangeEvaluator.Evaluate` calls in Late Move Reductions (LMR).
  2. Added shallow SEE pruning: pruned losing captures at `depth <= 5` if `CurrentSee < -60 * depth`, and pruned quiet moves blundering material at `depth <= 4` if `quietSee < -35 * depth * depth`.
  3. Achieved **+16.3 &plusmn; 5.9 Elo** across a full 10,000-game match (**52.35% score**, 4,141 W / 3,671 L / 2,188 D, +470 win differential) with **100% LOS**. Estimated Anak Elo increased to **2503 &plusmn; 6**, breaking the 2500 milestone.

### 7. `v1.0.7` — Correction History Side-to-Move Partitioning (+1.1 Elo)
- **Files Modified:** `src/Anak.Search/Minimax/History/CorrectionHistory.cs`
- **Mechanism:** Expanded correction history table to `short[2 * 16384]` and partitioned indexing by `[SideToMove, PawnKey]`. Restores Negamax mathematical symmetry by preventing White and Black nodes from overwriting each other's corrections with opposite signs.
- **Validation:** Over 4,000 games at `3+0.03` against `v1.0.6`, scored **2,006.5 / 4,000 (50.16%)**, yielding **+1.1 &plusmn; 9.2 Elo** (1489 W / 1476 L / 1035 D) with zero regression. Released as baseline `v1.0.7` (**2504 &plusmn; 9 Elo**).

## 📋 Complete Active Work Queue (Targeting `v1.0.8+`)

Here are the remaining active improvement and bugfix candidates, organized by priority:

### 1. Step 2.12 — Detect 2-Fold Repetition Inside the Search Tree (`IsRepetition`) *(Bugfix: High Impact)*
- **Files:** `src/Anak.Core/Board/Board.cs`, `src/Anak.Search/Minimax/AlphaBetaEngine.cs`
- **Bug Found:** At `ply > 0`, `AlphaBeta` calls `board.IsThreefoldRepetition()`, which requires `count >= 2` prior occurrences in `_history` (3 total occurrences). Waiting for 3 occurrences inside the search tree wastes 4+ plies of search depth and blinds the engine to perpetual checks and repetition defences until `depth >= 8+`.
- **Fix:** Add `board.IsRepetition(int searchPly)` that returns `true` on the 2nd occurrence if the earlier occurrence is within the current search tree (`i >= _gamePly - 1 - searchPly`), or on the 3rd occurrence if both prior occurrences predate the root.
